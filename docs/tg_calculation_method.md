# Next方式とTG方式の切替

画面上部の「計算方式」で `next`（従来方式）または `tg`（TG比較方式）を選びます。
初期値はNextです。方式の指定がない旧入力JSONもNextで計算します。
TGの仕様識別子は `tg-2026-10-v1`、入力スキーマは `261021` です。

## 操作

1. 計算方式を選択します。
2. 住宅・外皮・暖冷房設備を設定します。TGはダクト式（方式1）とRAC活用型（方式2）に対応します。
3. TGの場合、上部に表示される送風機指数 `n` を選択します（1、1.5、2、3）。
4. RAC活用型の場合、TG用の定格暖房能力・定格冷房能力・効率区分（い・ろ・は）を入力します。
5. 暖房・冷房の最低風量を必要に応じて入力し、計算します。

TGで最低風量を入力しない場合、暖房期は暖房設計風量、冷房期は冷房設計風量を使います。
中間期は両者の大きい方です。直接入力した場合も、中間期は暖冷房の大きい方です。
両季節に同じ数値を入力すると、全期間でその数値を使うTGの条件に対応します。
全般換気ありでは最低風量に居室全般換気量合計の下限を適用します。
下限適用後の最低風量が設計風量を超える入力はエラーにします。

TGに切り替えると床下空調・熱の繰越・Nextの熱源機定風量制御はOFFになります。
JSONからこれらを同時に指定した場合も計算開始前にエラーにします。
床下空調を比較するときはNextを選択してください。
方式3（潜熱評価モデル）、方式4（電中研モデル）はTGでは選択できません。
暖冷房の全般換気機能は同じ設定にしてください。

## 計算上の違い

| 項目 | Next | TG |
| --- | --- | --- |
| 既存計算 | 従来の設定と計算を維持 | 下記の処理に切替 |
| 居室の全般換気量 | 最低風量入力に応じた既存の再配分 | 元の全般換気量を住宅負荷計算に保持 |
| VAV調整前の区画配分 | 既存の選択方式 | 床面積比（式44・45） |
| VAV調整後の風量 | 既存のキャップ・最低風量処理 | 床面積比で最低風量を配分し、区画ごとの上限で制限（式43） |
| 全般換気なし | 既存の補正スイッチに従う | 給気の区画下限から全般換気量を除外 |
| 送風機の総電力 | 既存のSFP・最低電力・近似方式 | `P_rtd × (V / V_design)^n` |
| 送風機の暖冷房分 | 既存の計上方法 | 総電力から最低風量までの電力を差し引く |
| 送風機の換気相当分 | 従来出力 | 暖冷房期は最低風量まで、中間期は全量を別計上 |
| RAC暖房性能 | 既存の入力・算定方式 | 定格暖房能力から換算した冷房能力 `(q_H + 85.1) / 1.2090` を使用 |
| RAC消費電力 | 既存の処理負荷上限を含む | ダクト計算の平均出力に効率曲線を適用し、RAC側で再度負荷を上限制限しない |

TGでは暖冷房期のサーモOFF時も、最低風量までの送風機電力を換気相当分として計上します。
全般換気なしでは中間期の圧縮機電力・送風機電力・未処理負荷をゼロにします。
中間期の内部計算風量はゼロに置き換えないため、風量列の正値は稼働電力を意味しません。
非稼働季節の温度・湿度診断値は未定義になる場合があります。

出口温度の計算法と冷房間仕切り熱移動の補正は共通の独立設定です。
TGを選択しても自動的にONにはしません。
Next専用の最低送風機電力・換気分控除スイッチ・SFP・VAV配分変更などはTGでは使用せず、画面で非表示になります。

### RACと既定送風機

TGのRAC性能は、TG用の能力と効率区分から算定します。
Next用の最大能力・定格効率・能力補正係数の入力は使用しません。
小能力時高効率型コンプレッサーの設定は暖冷房それぞれの既存入力を使用します。
能力補正は暖房0.8、冷房0.85、冷房吸込湿度補正1.15、RACデフロスト係数0.77
（外気温5℃未満・相対湿度80%以上）です。
暖房消費電力ではダクト平均出力に含まれるデフロスト補正をTGの式に従って扱います。

RACの送風機既定風量・電力は、床面積から算定したダクト式の能力を基に算定します。
設計風量の直接入力は優先します。ダクト式では既存の機器仕様入力も使用できます。

**未処理冷房負荷の互換処理：** 建研3.10の未処理冷房負荷経路には、既定冷房風量の算定で
暖房側の定格送風機関数を呼ぶ箇所があります。TGのRAC置換では、この関数は床面積基準の
暖房側風量を返します。参照計算を再現するため、設計風量を直接入力しないTGの方式2では、
未処理冷房負荷をその風量で別途計算します。冷房電力と通常の診断出力には冷房側風量を使います。
したがって、`output2` の未処理冷房一次エネルギーと、通常冷房パスの区画別未処理負荷診断は
算定風量が異なります。Nextにはこの互換処理を適用しません。

## 結果の見方

暖冷房の `E_H` / `E_C` は、熱源機・送風機の暖冷房分と未処理負荷の一次エネルギー相当分です。
TGでは次の列を追加し、画面にも内訳と合計を表示します。

| 年間CSV（output1） | 内容 |
| --- | --- |
| `calculation_method` | `tg` |
| `E_fan_vent [MJ/year]` | 送風機の換気相当電力の一次エネルギー換算 |
| `E_vent_ch5 [MJ/year]` | 第五章の換気相当分 |
| `E_total_TG [MJ/year]` | `E_H + E_C + E_fan_vent + E_vent_ch5` |

時刻別CSV（output2）には `E_E_fan_vent_d_t [kWh/h]`、`E_E_vent_ch5_d_t [kWh/h]`、
`E_total_TG_d_t [MJ/h]` を追加します。
暖冷房の定数CSV（output3）には、実際に用いた季節別最低風量 `TG_V_hs_min_H/C/M` を記録します。
既存の `V_hs_min` 列は元の居室換気量合計です。

第五章相当分は `SFP × A_A × 2.4 × 0.5 × 1.1 × 8760 × 0.001 × 9.76` です。
SFPは全般換気ありで0.3185、なしで0.4 W/(m³/h)を使います。
局所換気を含まない比較用の集計であり、住宅全体の法定一次エネルギー評価値ではありません。

保存入力JSONにはTGの算定済みRAC性能も記録します。
manifestには計算方式とTG仕様識別子を記録し、TG入力ハッシュは保存した入力JSONと一致します。

## JSONの追加項目

通常の入力JSONに、次の項目を加えます。

```json
{
  "calculation_method": "tg",
  "tg_fan_exponent": 1.0,
  "tg_q_rtd_H": 6700,
  "tg_q_rtd_C": 5600,
  "tg_rac_class": "い"
}
```

これは追加項目だけの例です。住宅・外皮・H_A・C_Aなどの通常入力も必要です。
RAC項目はそれぞれの設備が方式2の場合だけ使います。
`calculation_method` の省略または `next` の指定で従来計算になります。

## 検証

- NextのPhase 5既存2ケースについて、年間・8760時間CSVの数値基準を維持します。
- 公開テストは入力検証、旧JSON互換、計算コンテキストの復元、区画最低風量、
  送風機電力の収支、年間集計、方式情報、画面の切替を検証します。
- 別途、参照実装との56条件の関数比較を実施しました。
  風量・送風機電力は一致し、RAC電力の最大絶対差は約8.6e-14 kWh/hでした。
- 標準住戸・地域6・省エネ基準外皮の年間比較では、ダクト/RAC、全般換気あり/なし、
  最低風量300/設計風量、VAVあり/なしを組み合わせた4ケースの各内訳が一致しました。
  合計の最大絶対差は約1.5e-11 MJ/年でした。
- この比較はすべての入力組合せの一致を保証するものではありません。
  外部気象・負荷データ、暖冷房別の異なる最低風量、機器仕様の直接入力などは、
  本プラットフォームの共通入力として扱う拡張です。

参照スクリプトはこのリポジトリに含めません。
建研由来の `pyhees` 関数を差し替えず、`jjjexperiment` 内の実行単位のコンテキストで分岐します。
